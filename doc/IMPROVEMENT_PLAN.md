# DaVinci Code 项目提升方向与实施建议

本文档记录当前项目的主要改进方向。目标是将项目从“功能完整的多人桌游原型”逐步提升为安全、稳定、可扩展、易维护的生产级多人应用。

## 总体判断

当前项目已经具备完整的业务闭环：注册登录、房间大厅、多人对局、聊天、结算、战绩和管理员页面。主要技术问题集中在以下四个方面：

1. 服务端没有真正掌握认证和对局控制权。
2. 高频 HTTP 轮询会带来较大的数据库压力。
3. 完整 JSONB 状态覆盖更新存在并发丢数据风险。
4. 部署、测试、监控和数据库迁移体系还不完善。

本文档按照 P0 → P1 → P2 进行优先级分层：

- **P0：必须优先处理的安全和核心可信度问题**，否则不适合公开部署。
- **P1：影响正确性、并发能力和页面读取性能的问题**，用于提升系统稳定性和可扩展性。
- **P2：体验、工程质量和长期运维问题**，用于完善产品质量。

文档末尾的“推荐实施顺序”将这些优先级进一步整理为四个阶段。因此，整体方向是从 P0 到 P2 逐级提升，但同一优先级内可以根据实际资源并行推进。

## P0：安全与对局完整性

### 1. 建立真正的服务端认证体系

当前用户身份主要保存在浏览器 `sessionStorage`，多个 API 直接信任请求体或查询参数中的 `username`。例如：

- `src/app/page.tsx` 将用户信息写入 `sessionStorage`。
- `src/app/api/admin/users/route.ts` 通过 `adminUsername=admin` 判断权限。
- 房间和游戏接口接收客户端提交的 `username`。

建议：

- 密码使用 Argon2id 或 Bcrypt 哈希，禁止使用 Base64 作为密码存储方案。
- 登录成功后签发服务端会话，推荐使用 HttpOnly、Secure、SameSite Cookie。
- 每个 API 从 Cookie/Session 中解析当前用户，不再信任请求体中的用户名。
- 增加服务端权限模型，例如 `player`、`admin`、`room_host`。
- 增加会话过期、主动注销、密码错误次数限制和登录频率限制。

### 2. 改为服务端权威对局

当前客户端可以提交完整 `gameState`，服务器基本只负责保存。这会导致玩家可以伪造摸牌、猜牌、回合、获胜者甚至其他玩家的手牌。

建议将操作改成领域动作 API：

- `POST /game/draw`
- `POST /game/guess`
- `POST /game/pass`
- `POST /game/surrender`
- `POST /game/reposition-joker`

服务端负责验证：

- 当前用户是否属于房间。
- 是否轮到当前用户。
- 当前回合状态是否合法。
- 牌是否仍存在于牌堆。
- 猜测目标是否为其他玩家的未公开牌。
- 猜测值是否符合牌面规则。
- 是否已经结算过。

客户端只提交动作参数，不能提交完整对局结果。

### 3. 防止隐藏牌泄露

`GET /api/rooms/[roomId]/game` 当前会返回完整 JSONB，其中包含所有隐藏牌的真实值。即使 UI 不展示，浏览器开发者工具仍可读取。

建议：

- 服务端根据当前用户生成“玩家视图”。
- 当前玩家可以看到自己的手牌真实值。
- 其他玩家的未公开牌只返回 `id`、颜色、位置和 `isRevealed`。
- 结算后才返回全部牌面。
- 日志和聊天内容也应按权限过滤。

### 4. 保护管理员接口和数据库

当前管理员接口仅通过 URL 参数判断身份，属于可伪造权限。Docker 脚本还包含硬编码数据库密码，并将 PostgreSQL 配置为公网访问。

建议：

- 管理接口使用服务端 Session 和角色校验。
- 删除 `?adminUsername=admin` 这类权限判断方式。
- 所有数据库密码、管理员初始密码改为部署环境密钥。
- 默认管理员首次登录后必须修改密码。
- 本项目部署要求 PostgreSQL 可被 Docker 宿主机及外部业务客户端访问，因此不以“禁止暴露 5432”作为验收条件；必须通过防火墙/安全组、强密码、最小来源网段和独立数据库账号控制访问范围。
- PostgreSQL 对外监听属于明确的部署需求。本项目当前明确不实施 PostgreSQL TLS，连接安全由强密码、服务器防火墙/云安全组和最小权限数据库账号保障；如未来部署到不可信公网，再单独评估 TLS 或 VPN。
- 应用数据库账号不应使用 PostgreSQL SUPERUSER；容器初始化账号与应用运行账号应分离。

### 5. 无邮箱场景下的密码重置方案

本项目暂不引入邮箱系统，因此不能仅凭用户名允许用户自助重置密码，否则无法证明请求者就是账号本人。推荐采用以下策略：

#### 主方案：管理员临时密码重置

1. 管理员通过受保护的管理后台选择需要重置的用户。
2. 服务端生成一次性随机临时密码。
3. 数据库只保存临时密码的 Argon2id/Bcrypt 哈希，不保存明文密码。
4. 临时密码设置有效期为 30 分钟，或限制为只能成功登录一次。
5. 管理员通过其他可信渠道将临时密码告知用户。
6. 用户使用临时密码登录后，强制设置新的个人密码。
7. 重置完成后注销该用户已有会话，并记录管理员操作日志。

建议增加以下用户字段：

```text
users.must_change_password
users.password_reset_expires_at
users.password_reset_by
```

不建议使用以下方式：

- 仅凭用户名直接重置密码。
- 使用生日、密保问题等弱验证。
- 让管理员查看或恢复原密码。
- 将临时密码写入日志或以明文持久化。

在不引入邮箱的前提下，统一采用“管理员临时密码重置”方案。:codex-annotation{index="1"}

## P1：正确性、并发与性能

### 1. 并发一致性与数据正确性

#### 1.1 为对局状态增加版本控制

当前 `game_states` 是完整 JSONB 覆盖更新，多个玩家同时提交时可能出现后写覆盖先写。

建议增加：

- `version`：每次成功动作递增。
- `updated_by`：记录执行动作的用户。
- `last_action_id`：用于幂等处理。

更新时使用类似条件：

```sql
UPDATE game_states
SET game_data = $new_state, version = version + 1
WHERE room_id = $room_id AND version = $expected_version;
```

版本不匹配时返回冲突，让客户端重新拉取状态。

#### 1.2 对结算流程增加事务和幂等性

当前 `endGame()` 可能被多个客户端重复调用，用户战绩和历史记录存在重复写入风险。

建议：

- 为每局游戏创建唯一 `match_id`。
- `match_history` 增加 `(match_id, username)` 唯一约束。
- 使用数据库事务同时更新房间、用户战绩和比赛历史。
- 结算前通过状态机判断是否已经结束。
- 统计更新改为单条批量 SQL，避免逐个用户循环更新。

#### 1.3 明确房间状态机

当前房间状态主要在 `waiting` 和 `playing` 之间切换，`finished` 基本没有实际使用。

建议定义明确状态：

- `waiting`：等待玩家。
- `playing`：对局进行中。
- `settling`：结算事务执行中。
- `finished`：结算完成，等待下一局或关闭。
- `closed`：房间已关闭。

所有状态迁移应由服务端原子操作完成。

#### 1.4 改进离线清理和在线状态模型

目前使用 `users.last_login_at` 判断在线状态，并在读取房间时执行离线玩家清理。

建议：

- 新增独立的 `user_presence` 或 `room_sessions` 表。
- 区分登录时间、最后心跳、最后房间活动时间。
- 离线检测使用定时任务或专门的清理 Worker。
- 页面进入后台时降低心跳频率，网络恢复时主动重连。
- 清理操作增加事务和幂等保护，避免重复踢人。

#### 1.5 限制 JSONB 数据规模

`game_data` 同时保存牌局、日志和聊天，聊天没有明确上限，长期可能导致单行数据不断变大。

建议：

- 日志只保留最近 N 条。
- 聊天拆到独立的 `room_messages` 表。
- 对局动作拆到 `game_actions` 或事件表，便于审计和回放。
- 对 JSONB 设置最大大小和服务端字段白名单。

### 2. 实时同步与页面读取速度

#### 2.1 优先从短轮询迁移到事件驱动同步

房间页面每 1.5 秒同时请求房间、游戏状态和用户战绩，首页每 3 秒请求房间列表，Footer 每 4 秒请求在线人数。

在多人场景下，这会产生大量重复 HTTP 请求和数据库查询。

推荐方案：

1. 使用 WebSocket 或 Socket.IO 推送房间和对局事件。
2. 或使用 SSE 推送单向状态变化。
3. PostgreSQL 可以通过 `LISTEN/NOTIFY` 作为跨实例事件源。
4. Redis Pub/Sub 适合多实例部署时做事件广播。

如果暂时保留轮询，应至少做到：

- 合并房间、游戏和用户信息接口。
- 使用 `version`、`ETag` 或 `updated_at`，没有变化时返回 304。
- 使用 `AbortController` 取消过期请求。
- 页面不可见时暂停或降低轮询频率。
- 网络失败时指数退避。
- 防止上一次请求未完成时再次发起相同请求。

#### 2.2 优化数据库查询

建议为以下字段建立索引：

- `rooms(status, created_at)`
- `room_players(room_id)`
- `match_history(username, started_at)`
- `users(last_login_at)`
- `game_states(updated_at)`

同时避免每次读取房间列表都执行过期房间删除，改成定时任务或数据库 Job。

#### 2.3 减少完整状态写入

对局动作应尽量保存“动作结果”或局部字段，而不是每次将整个牌堆、所有手牌、日志和聊天重新序列化并写入 JSONB。

可以采用：

- 当前状态表 + 动作事件表。
- JSONB 只保留当前快照。
- 每隔若干动作生成快照，历史动作单独保存。

## P2：体验、前端性能与工程质量

### 1. 首屏性能与前端包体

#### 1.1 合理使用 Server Components

当前首页、房间页、战绩页和管理员页都以客户端组件为主。建议：

- 页面外壳、标题、说明和静态布局使用 Server Components。
- 只有需要交互的表单、棋盘和弹窗使用 Client Components。
- 将房间棋盘、管理员表格、Framer Motion 等较重区域动态加载。

#### 1.2 清理无用依赖

检查并移除未使用的 Supabase、Socket.IO、Redis、MySQL、Zustand 等依赖，降低安装时间、Docker 镜像大小和潜在客户端包体。

#### 1.3 优化构建和容器

- 使用 `npm ci`，不要使用无锁定的 `npm install`。
- 使用多阶段 Docker 构建。
- 生产镜像只保留运行所需文件。
- 增加 `.dockerignore`，排除 `.git`、文档、缓存和本地数据。
- 使用非 root 用户运行 Node 应用。
- 增加健康检查和优雅关闭逻辑。

---

### 2. UI、可访问性和交互体验

#### 2.1 动画和视觉细节

- 用精确的 `transition-transform`、`transition-opacity` 等替代 `transition-all`。
- 减少高频 `animate-pulse` 和 `animate-bounce`，避免视觉疲劳。
- 支持 `prefers-reduced-motion`。
- 为图片或卡牌增加统一的低透明度轮廓和层级阴影。
- 保持嵌套容器圆角的同心关系。

#### 2.2 可访问性

- 对手卡牌不要只使用可点击 `div`，改为可键盘操作的按钮。
- 弹窗增加焦点捕获、ESC 关闭和 ARIA 标识。
- 使用 `aria-live` 播报回合、错误、断线和结算状态。
- 不要只依赖颜色区分胜负、在线、出局等状态。
- 检查移动端最小点击区域和深色模式对比度。

#### 2.3 状态反馈

补充以下状态：

- 首屏骨架屏。
- 请求提交中和不可重复点击状态。
- 断线、重连、同步冲突提示。
- 对局状态过期提示。
- 乐观更新失败后的回滚和重试。

---

### 3. 测试、监控和工程质量

#### 3.1 测试

- `gameLogic.ts`：发牌、洗牌、排序、百搭牌位置、胜负判断。
- 认证接口：密码校验、会话、权限和限流。
- 房间接口：并发加入、房主转移、断线清理。
- 游戏接口：重复动作、非法动作、版本冲突、重复结算。
- Playwright 多浏览器 E2E：至少覆盖 2～4 个玩家的完整对局。

#### 3.2 可观测性

- 记录请求耗时、数据库查询耗时、轮询次数和 WebSocket 连接数。
- 接入错误追踪系统。
- 为数据库连接池、活跃房间、在线人数和结算失败建立指标。
- 增加数据库备份、恢复和数据清理演练。

#### 3.3 数据库治理

当前 `supabase_schema.sql` 与 `scripts/setup-pg.js` 存在表结构和命名差异。建议选择一个正式迁移来源，使用迁移版本管理数据库结构，避免开发、Docker 和生产环境出现漂移。

## 推荐实施顺序

### 第一阶段：安全止血

- 服务端 Session 和角色权限。
- Argon2id/Bcrypt 密码哈希。
- 服务端动作 API。
- 隐藏牌裁剪返回。
- 删除硬编码密码；保留 PostgreSQL 外部访问能力，但通过安全组、防火墙、来源网段和最小权限账号进行保护。本项目当前不启用数据库 TLS。

### 第二阶段：正确性和性能

- 对局版本号、事务、幂等结算。
- 房间状态机。
- 心跳模型独立化。
- 数据库索引和聊天拆表。
- 合并轮询接口并支持退避。

### 第三阶段：实时化和体验

- WebSocket/SSE 同步。
- Server Components 和动态加载。
- 动画、可访问性、断线重连和状态反馈优化。

### 第四阶段：长期工程化

- 完整测试体系。
- 监控和告警。
- 正式数据库迁移。
- 应用与数据库拆分部署。
- 备份恢复和压力测试。

## 验收指标建议

- 未登录用户无法调用任何房间或游戏动作。
- 客户端无法读取其他玩家未公开牌面。
- 同一局结算重复请求不会重复增加战绩。
- 4 人房间状态同步延迟稳定在 200～500ms 范围内。
- 页面进入后台后请求量显著下降。
- 数据库慢查询、错误率和连接池使用率可观测。
- 关键业务逻辑具备自动化测试覆盖。
